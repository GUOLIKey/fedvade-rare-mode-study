# 丢失定位

> **审核后的当前说明：** 旧“丢类”证据已撤回。本命令只做诊断；低/高1-NN、分量多数类和旧oracle不能单独识别瓶颈。旧全局tau oracle保留并标记历史口径。调用必须显式提供--output新路径。
> 正确入口和能力边界见 [代码说明](../../README.md)；下方为历史线路说明，其结论以根README和结论状态表为准。


**问的问题**：某些类生成不出来，问题出在编码器、客户端局部 GMM、服务器分量，还是解码器。

| 子命令 | 检查什么 |
|---|---|
| `mode-loss` | 服务器各分量装哪些类、死分量数、客户端局部 GMM 是否形成对应分量、潜空间 1-近邻纯度、每分量期望采样数 |
| `decoder` | 重构误差（服务器 vs 客户端）、oracle 覆盖率（把真实样本编码再解码，绕开 GMM 采样）、逐类类别均值基线 |

**结论**

- 潜空间里目标类高度可分（class 5/8/9 的 1-近邻纯度 0.76 / 0.87 / 0.86，随机水平 10%）
- **撤回“完全相同，因此问题不在聚合”**：重构误差接近不证明参数相同或排除聚合影响。本次bal_clusterlet/s0参数检查中，服务器与client0解码器不相同，最大参数绝对差约2.99e-5；客户端解码器之间相同。此检查仍不能识别生成质量的因果瓶颈，见`results/audit_20261126/decoder_parameter_check.json`。
- 但这两条在修好指标之后都不再支持"某类被丢弃"的结论，见 `coverage_metric/README.md`
